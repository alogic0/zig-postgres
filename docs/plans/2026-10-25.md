# zig-postgres improvement plan

Created 2026-10-25. Status: planned; implementation has not started.

Improve pool availability and row decoding first, then make live acceptance
independent of consuming applications. Follow with bounded health checks,
common helpers and pool statistics, in that order. Develop and validate each
candidate in isolated library and consumer worktrees before advancing the shared
library checkout. These changes address findings from downstream integration.

The reviewed baseline is `v0.3.0` with Zig 0.17.0.

## Confirmed behavior

A standalone loopback protocol fixture reproduced the following in Debug and
Safe. It used synthetic connections and values, without an application database.

| Case | Observed behavior | Required behavior |
| --- | --- | --- |
| Pool slot 0 is empty, slot 1 is idle and usable, new authentication stalls | Acquisition times out after 120 ms; the existing connection still answers a query | Borrow the ready connection before opening another |
| Boolean cell contains `tomato` | `getBool()` returns true | Checked conversion reports an invalid boolean |
| Boolean cell contains `not-boolean` | `getBool()` returns false | Checked conversion reports an invalid boolean |
| Boolean cell contains empty text | `getBool()` returns null | Distinguish empty text from SQL NULL |
| Column index is outside the row | `get()` returns null | Checked access reports an invalid index |

The acquisition behavior is in [pool.zig](../../src/pool.zig), in `acquireInternal`.
The conversion behavior is in [client.zig](../../src/client.zig), in `PgRow`;
[stream.zig](../../src/stream.zig) also returns null for an invalid column index.
The application's adapter already adds strict cell conversion and bounds checks.

Keep these regression cases in the library so they can run from any checkout.

## 1 Prefer ready pool connections

- [ ] Add a public-API regression with two authenticated connections. Release
  the second, discard the first, and stall new authentication. Verify that
  acquisition returns the existing connection without attempting a new one.
- [ ] Under the pool mutex, search available connected slots first. Reserve an
  empty slot only when no connected slot is available.
- [ ] Keep connection establishment outside the mutex. Preserve the caller's
  absolute acquisition deadline and the configured connection timeout.
- [ ] Preserve slot recovery and waiter notification after failed or canceled
  connection establishment. Return a connection acquired during a deadline race
  before propagating the error.

Acceptance: the reproduced case succeeds in Debug and Safe, with no additional
connection attempt. Also cover all slots busy, all slots empty, reconnect failure,
canceled waiters and concurrent acquisition/release/discard. Check slot ownership
and connection-attempt counts; use timing bounds only to detect hangs. Existing
transaction-state and abandoned-stream discard behavior must still pass.

## 2 Add strict row decoding

- [ ] Provide checked access for both `PgRow` and `BorrowedRow`, sharing the
  scalar conversion implementation. Invalid indices return `ColumnOutOfBounds`;
  SQL NULL remains distinct from an empty string.
- [ ] Add typed checked getters for required and nullable text, bool, integers
  and floating-point values. Required NULL returns `UnexpectedNull`; invalid
  text and integer overflow return explicit errors.
- [ ] Decode PostgreSQL boolean text using complete `t` and `f` values. Reject
  prefixes, arbitrary strings and empty text instead of silently coercing them.
- [ ] Keep streaming generation checks ahead of cell access. Typed getters must
  preserve borrowed-string lifetimes and report `StaleRow` after advancement.
- [ ] Introduce checked APIs additively for 0.3 consumers. Document and deprecate
  the permissive getters, migrate examples and consumer adapters, and schedule
  removal or signature changes in an explicitly documented release.

Acceptance: run the same value/bounds matrix against owned and streamed rows.
Include valid true/false, SQL NULL, empty text, the reproduced malformed values,
signed integer boundaries and overflow, floating-point round trips and stale
views. Define the treatment of PostgreSQL floating-point NaN/infinity explicitly;
keep it separate from the finite-only binding helper in phase 5.

## 3 Own standalone live acceptance

The current `ci` target runs offline checks and compiles network fixtures.
`build-live` compiles the verifier, whose execution requires the consuming
backend's database lease. Add an independent execution path for this library.

- [ ] Add an opt-in `test-live` target that creates an owned PostgreSQL 16
  fixture with a unique name and a dynamically allocated loopback port.
  Provision it through Docker with a small Zig runner; the library's runtime
  module remains independent of the fixture tooling.
- [ ] Pin the initial fixture to the following image and platform. The local
  image was inspected as PostgreSQL 16.13 on 2026-10-25. Use the digest for pull
  and run, and record the resolved image ID and server version in each report.
  Updating the pin requires rerunning the full live matrix.

  ```text
  docker.io/library/postgres@sha256:20edbde7749f822887a1a022ad526fde0a47d6b2be9a8364433605cf65099416
  platform: linux/amd64
  ```

- [ ] Apply absolute phase deadlines and an outer runner watchdog with the
  initial limits below. Cap every subprocess/poll by its phase's remaining
  budget; repeated polling must not renew the deadline. Record finite overrides
  in the report. Driver operation deadlines remain independent and shorter.

  | Runner operation | Initial maximum |
  | --- | ---: |
  | Image pull | 180 seconds |
  | Other Docker commands and certificate-generation commands | 30 seconds per command |
  | Database startup and readiness polling | 60 seconds total |
  | Each test case | 30 seconds |
  | Test execution for one profile/TLS combination | 300 seconds total |
  | Whole fixture run, including image preparation and startup | 600 seconds |
  | Cleanup after success, failure, timeout or interruption | 30 seconds total |

- [ ] On timeout or interruption, cancel driver tasks and terminate/reap owned
  subprocess groups under bounded waits. Give cleanup its own absolute budget,
  even after the run deadline expires. A failed or timed-out cleanup must fail
  the run and report exact owned resource identifiers for recovery. Allow the
  CI job enough time for the run budget plus cleanup before its final cutoff.
- [ ] Register cleanup before startup. Remove owned containers, volumes,
  certificates and temporary files on success, failure and cooperative
  SIGINT/SIGTERM; never discover and delete unrelated resources by a broad prefix.
- [ ] Give the standalone fixture its own ownership marker. Remove its need for
  backend-specific database names or schema leases while retaining the existing
  consumer verifier where needed.
- [ ] Reuse the generic protocol, parameter, transaction, network, streaming and
  TLS cases. Include pool and decoder regressions and reusable fault cases.
  Consumers test their own application SQL.
- [ ] Run trusted TLS, wrong CA/identity, refusal, stalled handshakes, encrypted
  cancellation and lost COMMIT responses using owned certificates and peers.
- [ ] Emit a small JSON report with the library/compiler/server/OpenSSL versions,
  image digest/ID/platform, optimization/TLS settings, configured deadlines,
  cases, resource measurements and cleanup outcome.
- [ ] Keep default builds and offline CI usable without Docker or PostgreSQL.
  Document live prerequisites and an explicit CI job that invokes the live matrix.

Acceptance: run Debug/Safe with plaintext/TLS from the isolated library checkout
without sibling application repositories. Verify failed startup, interrupted-run
cleanup, stalled Docker commands and a hung test case. Inject cleanup failure
and verify bounded failure reporting instead of an indefinitely waiting runner.
Cover locks, deferred errors, cancellation, bounded rollback, unknown commits
without replay, stale rows, limits, abandoned streams and connection recovery.
Report driver allocation measurements separately from process RSS.

## 4 Bound health checks

- [ ] Add `healthCheckOpts` with one absolute deadline covering acquisition and
  `SELECT 1`. Pass the remaining budget through existing acquisition/query APIs;
  recovery retains its separate bounded cleanup allowance.
- [ ] Retain the existing health-check wrapper for compatibility and document
  its timeout behavior. Recommend the bounded API for service health endpoints.

Acceptance: health checks time out when the pool is exhausted or the server
stalls, return or discard their borrower, and allow a subsequent healthy check
to succeed. Test cancellation separately and prove that query execution does
not receive a fresh full budget after waiting for acquisition.

## 5 Provide common consumer helpers

Consumers choose application pool sizes, business SQL and retry policy.

- [ ] Add an owned connection-URI parser for `postgres://` and `postgresql://`.
  Cover percent encoding, IPv4/IPv6, defaults, database paths and supported TLS
  options. Reject malformed escapes, NUL, duplicate options and unsupported
  security modes. Give decoded configuration strings an explicit lifetime.
- [ ] Add finite floating-point parameter binding with round-trip-safe text
  encoding. Preserve separate SQL/value transmission and admission before I/O.
  Reject NaN/infinity for this helper; exact decimal values remain explicitly
  represented rather than converted through binary floating point.
- [ ] Expose a checked optional row count for the final completed command.
  A simple query currently combines returned rows and retains its last
  CommandComplete tag. The helper reads only that final tag; it never sums
  counts across statements or infers a count from the combined result rows.
- [ ] Recognize exactly `INSERT 0 N`, `UPDATE N`, `DELETE N`, `MERGE N`,
  `SELECT N`, `MOVE N`, `FETCH N` and `COPY N`. Parse `N` as a nonnegative
  integer with overflow checking. Zero is a count; an empty tag or another
  command such as `CREATE TABLE` or `COMMIT` has no supported count and returns
  null. Malformed recognized tags return an error. Counts describe the final
  command's operation, so SELECT/FETCH counts do not mean rows were modified.
  COPY tag parsing does not add support for the COPY streaming protocol.
  These tag forms follow the
  [PostgreSQL 16 CommandComplete specification](https://www.postgresql.org/docs/16/protocol-message-formats.html).
- [ ] Add mixed-statement regressions: `UPDATE` affecting two rows followed by
  `SELECT` returning one yields a count of one; `SELECT` returning rows followed
  by a zero-row `UPDATE` yields zero; `UPDATE` followed by `CREATE TABLE` yields
  null. A later statement or deferred error returns an operation error rather
  than a successful count for an earlier statement. Exercise materialized and
  streamed completion paths.
- [ ] Add an optional-single-row helper: no rows returns null, one returns an
  owned row, and multiple rows return a cardinality error. Define cleanup and
  connection ownership on every exit, including deferred errors after a row.
- [ ] Share helpers across materialized and streaming paths where appropriate.
  A streamed operation is successful only after validated ReadyForQuery;
  provisional rows or command tags do not prove transaction completion.
- [ ] Replace equivalent consumer adapter code only after library acceptance
  passes, retaining the application's public database interface.

Acceptance: URI configuration survives freeing its input; malformed configuration
fails before network use. Parameter rejections leave the exchange untouched.
Verify float boundaries, zero/one/many-row results, every supported command-tag
form, mixed statements, cleanup and ownership. Rerun affected consumer contracts
after replacing adapter helpers.

## 6 Expose pool statistics

- [ ] Add a synchronized snapshot of idle, borrowed and connecting slots,
  current waiters, connection failures, reconnects and discards. Define each
  counter and distinguish initial connections from replacement connections.
- [ ] Keep snapshots free of credentials, SQL, parameters and customer values.
  Hold synchronization only while reading/updating counters, never during I/O.

Acceptance: verify snapshot consistency during concurrent acquisition, release,
discard, canceled waits and failed reconnects, with no leaked waiters or borrower
counts. Statistics must preserve the bounded health-check behavior from phase 4.

## Delivery and consumer adoption

Create the isolated worktrees before the first runtime change. Implement the
phases in order, committing each verified change separately in the candidate.
The pool fix can ship independently. Document checked getter names and compatibility
before migrating consumers. Add new APIs to `src/root.zig`, examples, README and
the changelog as they become available; keep unfinished items unchecked here.

The existing offline gate is:

```sh
zig build ci -j4 --summary all
```

Once phase 3 introduces `test-live`, run the proposed live matrix:

```sh
zig build test-live -j4
zig build test-live -Doptimize=safe -j4
zig build test-live -Dtls=true -j4
zig build test-live -Doptimize=safe -Dtls=true -j4
```

1. Record the library and consumer baselines and test each in an isolated worktree.
2. Provide the consumers' other local dependencies at recorded revisions in
   the test environment. Verify that both PostgreSQL dependency paths resolve to
   the candidate worktree. Run builds from the isolated checkouts and keep
   their installed artifacts, logs and fixture resources isolated as well.
3. Commit the candidate changes and run library acceptance against that exact
   revision. Run both consumers' affected isolated suites in Debug and Safe,
   including TLS builds, queue/credit/storage/API flows and snapshot import
   where applicable. Test the current consumer baselines as well as any commits
   that adopt the new helpers, so shared-checkout promotion has a compatible
   consumer configuration at each step.
4. Record the library commit and both consumer commits together in an acceptance
   receipt, with dependency revisions, compiler/settings, image digest/platform,
   commands and outcomes. Require clean tested source trees; any source change
   after testing requires a new recorded revision and affected checks.
5. After acceptance, recheck the shared checkout's branch, HEAD and worktree
   state against the recorded baseline. Advance it to the tested candidate
   using a fast-forward-only update. Preserve intervening changes; if the
   baseline moved, reconcile in isolation and repeat affected acceptance.
   Promote consumer helper changes in the order verified in step 3.
6. Retain the prior accepted library and consumer revisions for coordinated
   rollback. Record the promoted revisions in the consumer receipts. Restart
   application processes only as part of their separate deployment procedure.

Keep automatic write retries disabled and preserve unknown COMMIT outcomes
throughout implementation and adoption.

Completion requires the two reproduced cases to pass as regressions, standalone
live acceptance to run without application repositories, the common helpers and
bounded health/statistics APIs to be documented and tested, and affected consumer
acceptance to pass at the recorded library revision.
